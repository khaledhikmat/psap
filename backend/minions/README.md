## Minions

### Players

- minion workflows
    - are Go routines hosted by a pod
    - support signals only....no queries. Otherwise we will need to desrialize the data back to the caller.
    - maintain two ids: workflow IDs and business IDs
- minion workflows manager: 
    - usually it is a pod
    - workflow manager IDs are unique UUIDs.
    - registers as workflow manager so it can be disovered.
        - might impersonate another workflows manager's identity if one is found abandoned (no need for a monitor). 
        - hydrates its state and instantiate all associated workflows 
    - hosts minion workflows and communicates with them locally.
        - For new minion workflows, it creates a new minion workflow.
        - For existing ones, it delivers the payload to the workflow via its public interface...no remote call.
    - listens to its own queue (in the database), dequeues and signals workflow minions (including start and stop).  
    - maintains heartbeat to signal alive
    - maintains number of workers i.e. load
    - maintains active list of minion workflow ids. The stopped ones are gone. 
- minion client tries to locate the workflow: 
    - Workflow IDs are unique UUIDs generated by the client
    - If found, it places the workflow payload on that manager's queue. 
    - If not found, it places the workflow payload on any registered manager's queue.
    - It errors out if there are no registsred managers.

### Writing a minion

`Minion[S]` (`minion.go`) owns the lifecycle: mailbox, timers, periodic saves, start and stop. A kind of minion
supplies its state type `S` and overrides processors, as `simple.go` does:

```go
type MyState struct {
    MinionState        // gives S the Base() method the base minion needs
    Balance float64
}

m := NewMinion(id, managerID, "my", svcs, &MyState{}) // S is the pointer type
m.OnSignal = func(ctx context.Context, s *MyState, req MinionRequest) error { ... }
m.OnLoad = ...      // return ErrNoState when nothing is saved yet
m.OnSave = ...
m.OnStart = func(mn *Minion[*MyState]) { mn.RegisterTimer(...) }
m.OnRunInitialActivities / m.OnRunFinalActivities = ...
```

- Processors run one at a time on the minion's goroutine and may use the state freely. Outside code uses
  `Signal`, `State()` (a snapshot of the base state) or `View(fn)` (read access to the whole `S`).
- Override processors after `NewMinion` and before `Start`.
- The final activities and last save get a context that is not cancelled, so they can still use the database.

### Launch minion prototype

`launch.go` adapts the launch workflow's create, answer submission/finalization, tier calculation and approval,
nudge, persistence, and Shield-start steps to the minion lifecycle. Construct it with a unique launch ID (also
used as the persisted launch ID), a manager ID, the services, and `LaunchMinionOptions`. Use
`SubmitAnswers`, `FinalizeAnswers`, `ReviseAnswers`, and `ValidateTier` to enqueue commands, and `GetState`
to read the current launch snapshot.

This is not a drop-in replacement for the Temporal workflow: it has no replay or Continue-As-New, its state
queries are local snapshots rather than Temporal queries, and revisions are queued signals rather than
synchronous Temporal updates. Recovered approval waits receive a fresh seven-day deadline because the launch
record does not persist the original deadline; owner nudge schedules use the persisted creation time and counts.
A validated launch still starts Shield through the configured
flow service, so Shield may remain Temporal-backed. The manager must stop the minion after its launch reaches a
terminal state; the generic minion loop does not stop itself on domain-state changes.
